# Existing Laravel 12 → 13 upgrade — 2.0 candidate

This procedure was rehearsed on the **same disposable installation** on PostgreSQL and MySQL: PHP 8.4.28 / Laravel 12.25.0 → PHP 8.5.13 / Laravel 13.43.0, followed by restoring the original PHP/framework/code/config/lock/assets/database/uploads. It is local acceptance evidence, not permission to change a deployed consumer. The candidate is unpublished; pin the reviewed package source and complete lock rather than resolving an unavailable release tag.

1. The application owner inventories deployed runtime/extensions, Composer manifest/lock/vendor, customized `app/Admin` routes/controllers/bootstrap, config, published views/translations/assets, database IDs/relationships/grants, uploads/thumbnails and sessions/caches. The release operator takes coordinated database and upload backups plus code/config/assets/runtime/lock backups, verifies their hashes and proves restore access. Pause writes/workers and drain in-flight mutations/exports before the cutover. Never reuse this repository's synthetic fixture credentials or keys.
2. Clear config/routes/views and application caches with the **old working runtime** (`php artisan optimize:clear`). Retain application keys, cookie name/path/domain, guard/model/connection, disk roots/URLs and PHP session serialization unless a separately planned migration says otherwise. This rehearsal chooses explicit session invalidation at both forward and rollback transitions: users reauthenticate, remember tokens are revoked under the application's policy, and server-owned signed action/step contexts are refreshed. Do not assume cross-version active-session continuity.
3. Select the tested PHP 8.5.13 runtime/extensions and an audited lock containing Laravel 13.40+ and the candidate. In staging, resolve the application's Laravel/package changes together with Composer's normal platform/advisory checks (`composer require laravel/framework:^13.40 encore/laravel-admin:^2.0 --with-all-dependencies` once an approved release exists). Deploy the reviewed lock using `composer install`, then `composer check-platform-reqs` and `composer audit --locked`. Never use platform/security bypasses. No new package database migration is required by this candidate; existing package tables and identifiers stay in place. Review any separate host migration before executing it.
4. **Selectively update published files.** Compare each deployed asset to the old release's SHA-256. Replace unchanged package-owned files with candidate bytes, add new paths (including `AdminLTE/plugins/jQuery/jquery.min.js`), and preserve unrelated custom files. For changed distributed files, perform an explicit three-way merge and verify the security fix survives. The rehearsal preserves a customized distributed skin and a custom CSS file; it never forces publication over customizations. `admin:publish --force` and forced provider publication are unsuitable as an unattended upgrade. Back up and merge maintained published views/translations/config in the same manner.
5. Merge customized logout headers/clients to **POST plus CSRF**. The old GET/HEAD link no longer logs out; those methods safely redirect. Preserve custom header markup. If selecting JSON sessions, merge the MessageBag/array-compatible alert/toastr templates; no automatic PHP→JSON conversion occurs. Generic action/picker/widget requests now require a signed `_context` plus explicit boolean authorization/model policy or the declared class ability; check every batch record. There is no compatibility bypass. Reopen forms/workflows after upgrade to obtain fresh contexts. For independent copies of identical multistep workflows, supply stable explicit IDs; host steps remain untouched.
6. Rebuild only the required minified LTR/RTL bundles for the host's actual skin/locales with `php artisan admin:minify` when the optional minifier is installed. Publish all updated owned bytes, purge CDN/reverse-proxy/browser caches for replaced paths, rebuild config/route/view caches and restart long-lived workers. URL fingerprints reflect **published** bytes; they cannot repair stale files. The historical `jQuery-2.1.4.min.js` filename remains a current-byte compatibility alias. No Node runtime is required by consumers.
7. Reauthenticate and verify cached/uncached boot, login/profile/password/avatar preview/removal, CSRF failure/success, allowed/denied grants, CRUD, redacted operation-log view/delete, uploads and complete downloaded exports. Reconcile original IDs/counts/relations/grants and every preserved customization/upload hash. Record the one intended custom-header migration separately from unexpected drift. Resume writes only after the application owner accepts these results.

Other mandatory API changes: custom Excel exporters require the typed Excel4 properties (`protected ?string $fileName`) and `query()` contract in [export documentation](model-grid-export.md). CSV uses standard doubled quotes and an empty escape argument; consumers parsing the old backslash wire format must update. Request sort columns must be server-declared `sortable()`; request-supplied cast SQL is ignored. Native schema inspection replaces removed DBAL bridges; extension generators must use the native schema APIs. PostgreSQL schema plus table-prefix Eloquent `find` remains unsupported in that historical combination; use the explicit qualified lookup described in the test evidence. Tree parent `0` is the fixed root sentinel, not a supported node key; direct-child delete retains deeper descendants according to the documented contract.

Default administrator row-action hard deletion cleans its configured model's known raw avatar after commit. Custom thumbnail/retention policies and arbitrary host upload definitions need the declared controller/form path or a custom action. `retainable()` semantics remain unchanged. Audit input is redacted before persistence and on historical-row display; historical rows are not rewritten. Generic handler failures return controlled feedback rather than raw exception text.

## Rollback, triggers and owners

The application owner triggers rollback for failed boot/authentication, authorization drift, data/file/hash mismatch, incomplete exports or unacceptable performance. The release operator stops writes and workers, captures post-cutover changes for explicit reconciliation, clears incompatible caches, restores the **matching** old code/runtime/extensions/manifest/lock/vendor/config/published assets plus database and upload backups, then invalidates sessions/caches under the same reauthentication policy. A database restore may discard writes since the snapshot: the application owner must approve how those writes are recovered before reopening traffic. Restore uploads and database from the same recovery point. Rebuild old caches with the old runtime, restart workers, and verify original IDs/grants/relations/file hashes/customizations and native login/profile/CRUD/CSRF/uploads/exports before resuming writes. Do not run uninstall, regenerate admin files or reseed during rollback.

Validate this procedure in the application's own staging environment with coordinated database/upload backups and explicit restore checks. Keep operational evidence outside the source tree; package test fixtures do not replace an application-specific recovery plan. This repository does not retain the one-time upgrade rehearsal environment or task reports.
